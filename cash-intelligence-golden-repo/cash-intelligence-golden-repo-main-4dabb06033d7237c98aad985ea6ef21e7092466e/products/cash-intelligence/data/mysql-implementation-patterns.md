# 15. MySQL implementation patterns (decision B)

> **Approved architecture: the R1 design baseline (DEC-006).** Approved by the Cash Intelligence architecture owner on 2026-11-05, after the 2026-11-03 design review. Generated specs follow it; a spec that needs something different is a change here first (GOV-CI-004 in `projects/branch-automation-cash-intelligence/05-delivery/delivery-model-and-gates.md`). Open questions (§16) stay open until answered. Section numbers (§n), open questions (Qn) and decisions (A–I) use the architecture's own numbering; `products/cash-intelligence/architecture/architecture-overview.md` maps each section to its file, and the open questions are in `products/cash-intelligence/architecture/open-questions.md`. Citations: `BAP-nn` = `SRC-JIRA-BAP-001`, `TDD:n` = line n of `SRC-XR-TDD-001`, `research/nn` = `SRC-CI-RES-001` (see the source index).

| Need | Pattern |
|---|---|
| **Logical areas** | One database per tenant; table-name prefixes `ref_`, `cash_`, `cfg_`, … (`area.table` in this document). `ci_catalog` is its own database |
| **Portability** | MySQL 8.0.36+/8.4 features only, nothing specific to Aurora or HeatWave, so the open hosting choice (§16 Q21) needs no schema change. Schema changes are Flyway migrations (§14.1). The database holds no stored procedures or functions (DEC-028); views and triggers still have a definer, the per-database owner account of the row below (`'<database>__owner'@'%'`, and the catalogue's and the archive's own), never `@localhost`, and setting another DEFINER needs `SET_USER_ID` on 8.0 but `SET_ANY_DEFINER` on 8.4; creating triggers with binary logging on needs `log_bin_trust_function_creators = 1` in the parameter group (RDS/Aurora; verify on HeatWave); history triggers are generated from the table definition and regenerated by every migration that changes a versioned table |
| **Where logic lives** | In the services (DEC-028). Decisions are service code with unit tests. Bulk work (staging, fact recompute, rollups, end-of-day capture) is set-based SQL that the service issues on one connection in a transaction it owns; it is not rewritten row by row. SQL lives only in repository classes; time and configuration are bound as parameters, never read by the SQL (`UTC_TIMESTAMP()` and JSON reads of configuration stay out of statements). The database holds tables, keys, CHECK constraints, generated columns, views, the audit and history triggers, and grants declared table by table per role. Upserts keep MySQL's syntax; there is no dialect layer |
| **Definers and cross-database reads** | Views and triggers have a definer whose rights stop at its database: a locked account per tenant database (`<database>__owner`), one for the catalogue and one for the audit archive. Nothing in one database names another. The tenant's status, Kinective id and legal hold, its partners' grants, its source instances and EJ maps are local copies that ci-ingest writes on every change signal: it reads the catalogue with its catalogue credential and writes the copies with the tenant credential; only the ingest role can write them. An EJ source instance has no routing key in the catalogue (EJ rows route by the CO `TenantId`), so it enters a tenant's copy at onboarding and is then refreshed like the others; a provider grant missing from the catalogue is removed from the copy. Id allocation, the change-signal bump and job leases are statements the service runs with its catalogue credential before or after the tenant transaction, and a job confirms its lease there before it writes; audit archiving and offboarding run as steps of the maintenance job, each with the credential of the database it touches. A partner's grant is removed in the tenant first, so the partner is refused at once, then in the catalogue, which ci-service retries until it succeeds. So the catalogue, the archive and a dedicated tenant can sit on different MySQL instances (§14.1). The definers hold no global privilege. |
| **Tenant on every table** | Every table, including child and detail tables (lines, rule details, attachments, recipients), carries `tenant_id`, and its primary key leads with it — even where a snippet above omits it for brevity: `x_id BIGINT PK` is shorthand for `PRIMARY KEY (tenant_id, x_id)`, and an `AUTO_INCREMENT` id also gets its own index, which InnoDB requires (§14.1 says why, in a database per tenant). Exceptions: the global catalogues (including `ref.model_bin_map`), the tenant database's read-only copies of `ci_catalog` tables (`ingest.source_instance`, `ingest.ej_txn_type_map`; only the instances that route to that tenant, keyed like their masters), the `ci_catalog` tables, `acc.role_mapping` (`tenant_id` NULL = every tenant) and staging, keyed by source keys with `tenant_id` stamped at routing (§5.2) |
| **Timestamps** | `DATETIME(3)` holding **UTC** by convention (not `TIMESTAMP`, which ends in 2038). Session `time_zone = '+00:00'`. Branch-local conversion is done in one place, the services' java.time code with the JVM's tz database (business dates at ingestion, alert due times), never `CONVERT_TZ`, so two tz databases cannot drift apart. Pages that show local times convert in the service |
| **Versioning** (marked "versioned" above) | A `<table>_hist` copy with `valid_from`/`valid_to`, written by `AFTER UPDATE` and `AFTER DELETE` triggers; current rows carry `valid_from`. "As of" queries union current and history. History tables are partitioned by `valid_to` month for retention |
| **Filtered uniqueness** | A stored generated column that is NULL when the rule does not apply, under a UNIQUE index (MySQL allows many NULLs). Examples: `excl_target = IF(is_exclusive AND rule_active, CONCAT(rule_type,':',target_kind,':',target_id), NULL)`; `default_slot = IF(is_tenant_default AND is_active, rule_type, NULL)`; `active_child = IF(effective_to IS NULL, child_device_id, NULL)`; `open_slot = IF(resolved_at IS NULL, CONCAT(rule_id,':',device_id), NULL)` (one open breach per rule and device). Inactive rules release their slots. Conversely, a nullable column that must be unique as NULL is replaced in the key by a stored `IFNULL(col, 0)` column (`instance_scope`, `model_scope`, `tenant_scope`) |
| **Access scope** | Tenants by database and credential; within a tenant, every page query joins `acc.v_user_*_scope` on a bound `user_id` (§11). No session variables or per-connection state, so pools, proxies and read replicas all work |
| **Scope joins** | Bind the scope view on `user_id` in a top-level join or semi-join (`… IN (SELECT location_id FROM acc.v_user_rollup_scope WHERE user_id = ?)`), never inside an outer join or beside another non-mergeable view, where MySQL materializes it for every user; where the device scope must not drive a per-device view, fix the order with `JOIN_ORDER` / `STRAIGHT_JOIN` (`NO_MERGE` only materializes, it does not order); each page query's test checks its plan with `EXPLAIN ANALYZE` (§11 Performance) |
| **Queues and outboxes** | `ops.work_queue` and `ops.alert_dispatch` are written in the same transaction as the change that causes them; workers claim rows with `SELECT … FOR UPDATE SKIP LOCKED`; feeds and scheduled jobs are claimed by leases with a fencing epoch (§14.2); a natural primary key (`breach_id`, `alert_no`) makes a rerun a no-op |
| **Computed columns** | `GENERATED ALWAYS AS (…) STORED` |
| **Upserts** | `INSERT … ON DUPLICATE KEY UPDATE` (row alias syntax). Staging and fact recompute run in one transaction per (device, day) batch; location rollups are rewritten once per run |
| **Date arithmetic** | `DATE(x + INTERVAL n MINUTE)` for fixed offsets in SQL; IANA-zone conversion only in the services' java.time code (Timestamps row above) |
| **Analytical reads** | No columnstore: location rollup tables (§7.3a), compact natural-key clustering, and partition pruning. CSV exports stream with server-side cursors, not one big result set |
| **Median / percentiles** (TCR usage quadrant, top/bottom 5%) | Window functions: `ROW_NUMBER()` and `COUNT(*) OVER ()` (no built-in percentile function) |
| **Append-only audit** | INSERT-only grant, rejecting triggers and a hash chain (§13) |
| **JSON** | Native `JSON` type for configuration and run metadata only; never for queried facts |
| **Character set** | `utf8mb4` with `utf8mb4_0900_ai_ci` (case-insensitive email lookup works natively) |
| **Encryption** | InnoDB tablespace encryption, or the managed service's at-rest encryption |

**Query rules** (measured in `research/80` §9, warm, Admin; each page's queries ship with its endpoint, whose end-to-end test checks
their scope binding and time):

1. **Filter and join on stored key columns** — `device_id`, `location_id`, `business_date` — never on generated,
   computed or roll-up-derived columns (`v_device_rollup.rollup_*` is a `COALESCE` and cannot use an index). Filter a
   device drill by the device's own `location_id` (a coin sits in its TCR's branch); join aggregates on `device_id`.
   Historic EOD 180 d went from 3.2 s to 0.35 s and Branch Cash Positioning 180 d from 26 s to 1.2 s.
2. **Resolve effective rules once per rule, not per device-day**: count devices per effective schedule first, then
   expand the few schedules over the dates. ATM Replenish History 90 d went from 4.2 s to 1.0 s.
3. **Dashboard widgets run in parallel** — each widget a separate API request on its own connection — or read a small materialized per-device 90-day aggregate, refreshed like projections (P11). Run one
   after another, the Admin dashboard took 2.1 s.
4. **Exports stream** raw lines in primary-key order through a server-side cursor; the API pivots denominations into
   columns and merges coin. Never `GROUP BY` the whole export in SQL: the enterprise 90-day CSV's first row went from
   20.8 s to 2.5 ms. Very large exports run as background jobs, under the requesting user's scope, that write a
   file to the tenant's bucket; the export is logged by `audit_log_export`, and the file's retention needs Legal review.

Source systems are read by the ingestion connectors with their own drivers; nothing in CI depends on the sources'
database engine.
